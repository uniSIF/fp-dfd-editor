# Copilot エージェントとの連携

FP DFD Editor の DFD を Microsoft Copilot のエージェントに渡して、DFD の作成・見直しを手伝ってもらい、その結果を取り込むための手順です（要件 FR-IO-01〜04）。
1 つの機能の見直しだけでなく、複数の機能の DFD を参考に、同じ種類の別の機能の DFD をまとめて作ってもらうこともできます。

## 仕組み

1. **書き出す**: ツールバーの「Copilot 連携」→「Copilot 用に書き出す…」で、書き出す機能を選びます（1 つでも、複数でも、すべてでも可）。選んだ機能の DFD と開発区分・外注業者が JSON（`"format": "fp-dfd-exchange"`、`"version": 2`）になります。JSON には作業ルールの要約と、同じソフトウェアの既存の分類・機能・外注業者・外部エンティティ・データファンクションの一覧（`catalog`）も入ります。
2. **依頼する**: 依頼を書いて「依頼文と JSON をコピー」を押し、Copilot に貼り付けます。JSON をファイルに保存して添付してもかまいません。Copilot は判断に迷う点があると、JSON を返す前に選択肢とおすすめを添えて質問してきます。回答すると JSON が返ります（「おまかせ」と答えた点は Copilot が推測し、仮定を返答に書きます）。
3. **取り込む**: Copilot が返した JSON（返答全体を貼ってもよい）を「Copilot の出力を取り込む…」に貼る（JSON を保存したファイルを、ダイアログにドラッグ＆ドロップするか「ファイルから読み込む…」で選んでもよい）と、機能ごとに差分（新しい分類・機能、要素の追加・変更・削除、データフロー）が一覧で表示されます。確認して「取り込む」を押すと反映されます。取り込みは 1 回の Undo で戻せます。

Copilot には、作成・変更した機能だけを、各機能の DFD の **完成形** で返してもらいます（差分ではなく、取り込み後にその DFD に置くすべての要素を書く）。アプリが差分を計算するため、エージェントが部分的な変更の書き方を誤る心配がありません。

### 依頼の例

- 参考にして新しい機能を作る: 「顧客登録」「顧客検索」を書き出し、「これらを参考に、顧客管理 / 取引先情報 に『取引先登録』『取引先検索』の機能を作ってください。取引先マスタは新しい ILF にしてください」
- 開発区分・外注業者を指定する: 「取引先登録は改修、外注は B社にしてください」
- まとめて見直す: すべての機能を書き出し、「各機能の複雑度を見直し、根拠（DET・FTR）を description に書いてください」
- 1 つの機能に追加する: 「顧客登録」を書き出し、「CSV ファイルから顧客を一括登録する処理を追加してください」
- 取り込みでエラーが出たとき: 「取り込み時に次のエラーが出ました。直した JSON を返してください: （エラー文）」

### 識別子（key）

| 対象 | key |
|---|---|
| 既存の機能 | 内部 ID（書き出した `features[].key`、`catalog.features[].key`） |
| エージェントが新しく作る機能 | 任意の文字列（例: `NEW-F1`）。`name`・`category1`（大分類）・`category2`（中分類）も書く |
| データファンクション・トランザクションファンクション・外部エンティティ | 表示番号（`DF-001`、`TF-002`、`EE-001`） |
| 非計上プロセス | `NCP-<内部 ID>` |
| エージェントが新しく作る要素 | 他と重ならない任意の文字列（例: `NEW-1`） |

入力元と出力先の 2 か所に分けて置いている外部エンティティ（FR-DF-18）には `"split": true` が付きます。取り込み時に `split: true` の外部エンティティは 2 か所に置き、`from` に書いたデータフローは左、`to` に書いたデータフローは右のノードにつなぎます。

外部エンティティとデータファンクションはソフトウェア全体で共有します。新しく作ったものを複数の機能で使う場合は、同じ key を書きます。新しいデータファンクションの所有機能（FP を計上する機能）は `owner` に機能の key で書きます（省略時は最初に書いた機能）。トランザクションファンクションと非計上プロセスは機能ごとのもので、key を機能間で共有できません。

### 取り込みのルール

- 機能の開発区分（`devType`: 新規 / 改修）と外注業者（`vendor`: 業者名、外注なしは空文字）を反映します。新しい機能で開発区分を省略すると「新規」、外注業者を省略すると未選択です。既存の機能で `vendor` の項目がなければ外注業者は変えません。設定画面に登録していない業者名や、新規・改修以外の開発区分は警告を出して反映しません。
- 新しい機能は、`category1` / `category2` の分類の下に作ります。分類がなければ作ります（プレビューに表示）。
- 機能の key が書き出したものと一致しない場合（エージェントが内部 ID を書き換えた、`NEW-F1` などを付けたなど）でも、名前（と分類）が同じ既存の機能が 1 つだけあれば、その機能を上書きします（警告で対応づけ先を表示）。同じ名前の機能が複数あって決められない場合は、新しい機能として追加します。
- 同じように、既存の機能の中で見つからない key の要素は、名前が同じ既存の要素（トランザクション・非計上プロセスはその機能のもの、外部エンティティ・データファンクションはソフトウェアのもの。データファンクションは種別も同じもの）が 1 つだけあれば、同じ要素として扱います。データフローもその要素につなぎ直して対応づけます。
- 既存の機能の名称・説明の変更は反映します。分類の変更は反映しません（ツリーで移動します）。
- 既存の key の要素は、名称・種別・複雑度・説明の変更を反映します。説明が空のときは今の説明を残します。
- 他の機能が所有するデータファンクションの変更は反映しません（その所有機能も出力に含まれている場合を除く。警告を表示）。外部エンティティの変更はソフトウェア全体に反映されます（警告を表示）。
- 次のものはエラーになり、取り込めません。エラーの内容をそのままエージェントに伝えれば直してもらえます。
  - 他の機能のトランザクションファンクション・非計上プロセスの key を使っている
  - 同じ機能の中や、機能をまたいだトランザクションの key の重複、種別の違う一覧への同じ key
  - データフローが同じ機能の dfd にない key を指している、接続ルール違反（外部エンティティ同士など）
  - 新しい機能に name・分類がない
- 「出力にない要素とデータフローを削除する」を選んだときだけ、出力に含まれる既存の機能について、出力にない要素を削除します（その機能のトランザクション・非計上プロセス・所有するデータファンクションは削除、それ以外は DFD から外すだけ）。既定では追加と変更だけを行います。出力に含まれない機能は変わりません。
- 新しい要素は空いている位置に置き、既定では取り込み後に変更した機能の DFD を自動整列します。
- 版 1 の JSON（1 機能: `feature` と `dfd`）も読み込めます。

## エージェントの作り方

### Copilot Studio / Microsoft 365 Copilot のエージェントビルダー

1. 新しいエージェントを作り、名前を「FP DFD アシスタント」などにします。
2. 「指示（Instructions）」欄に、下の「エージェントに与える指示」を貼ります。アプリの書き出しダイアログの「エージェント用の指示をコピー」でも同じ文面をコピーできます（約 5,300 文字。指示欄の上限 8,000 文字に収まります。プロジェクト固有の補足情報を入れるとその分増えます）。
3. 必要なら、見積もりの社内基準や業務の資料をナレッジとして追加します。
4. 使うときは、書き出しダイアログの「依頼文と JSON をコピー」の内容を貼り付けて送ります。機能が多く JSON が大きい場合は、「JSON をファイルに保存」したファイルを添付し、依頼文だけを入力します。

### プロジェクト固有の補足情報

業務の用語、要素の数え方の社内ルール、既存システムとの関係など、プロジェクト固有のドメイン知識を補足情報として入れられます（FR-IO-07）。書き出しダイアログの「エージェントの設定」にある「プロジェクト固有の補足情報」に書きます。補足情報はソフトウェアごとに保存され、保存ファイルにも入ります。

- 「エージェント用の指示をコピー」でコピーする指示の末尾に「# プロジェクト固有の補足情報」として足され、一般的な判定基準より優先するよう指示します。補足情報を変えたら、エージェントの指示を貼り替えてください。
- 書き出す JSON の `software.notes` にも入るので、指示を貼り替えていないエージェントや、通常の Copilot チャットにも伝わります。
- 指示欄の上限は 8,000 文字です。ダイアログに指示全体の文字数を表示し、上限を超えると警告します。長い資料は、エージェントのナレッジにファイルとして追加してください。

書く内容の例:

```text
- 「会員」は顧客マスタの別名。会員〜の画面は顧客マスタを更新する EI として数える
- 帳票は社内標準により、項目数にかかわらず EO・中 とする
- 基幹システム（SAP）の品目・取引先データは EIF として参照する
- 外部エンティティは「店舗担当者」「本部担当者」「基幹システム」の 3 つを使う
```

### エージェントを作らずに使う場合

通常の Copilot チャットを使うときは、書き出しダイアログで「エージェント用の指示（プロンプト）も含める」にチェックを入れてから「依頼文と JSON をコピー」を押します。指示・依頼・JSON がまとめてコピーされます。

## エージェントに与える指示

以下を Copilot エージェントの「指示」欄に貼ります（アプリの `src/domain/agentPrompt.ts` と同じ文面です）。

````markdown
# 役割
あなたは、FP 法（IFPUG ファンクションポイント法）で開発規模を見積もるための DFD（データフロー図）づくりを手伝うアシスタントです。
ユーザーは見積もりツール「FP DFD Editor」から書き出した JSON（"format": "fp-dfd-exchange"）を渡します。JSON の features には 1 つ以上の機能の DFD が入っています。
あなたはユーザーの依頼に従って、既存の機能の DFD を見直したり、渡された機能を参考に同じ種類の新しい機能の DFD を作ったりして、同じ形式の JSON で返します。ユーザーはあなたの JSON をツールに取り込みます。

# 受け取る JSON の読み方
- rules: 作業ルールの要約。必ず従う。
- software: 対象のソフトウェア。software.notes があれば、それはプロジェクト固有の補足情報（業務・用語・見積もりの決まり）なので、一般的な基準より優先して従う。
- features: 機能ごとの DFD。各機能は key（機能の識別子）、name（機能名）、category1（大分類）、category2（中分類）、description（機能の説明）、devType（開発区分: 新規 / 改修）、vendor（外注業者の名前。外注しないなら空文字）、dfd を持つ。
- dfd: externalEntities（外部エンティティ）、dataFunctions（データファンクション）、transactionFunctions（トランザクションファンクション）、nonCountedProcesses（FP に計上しないプロセス）、dataFlows（データフロー）。dataFunctions の owner は、その DF を所有する（FP を計上する）機能の key。owner がない DF はその機能が所有している。
- catalog: 同じソフトウェアにある既存の分類（categories）、全機能（features）、外注業者（vendors）、外部エンティティ、データファンクションの一覧。重複して作らず、使えるものは catalog の key をそのまま使う。

# 作業の進め方
1. 依頼を読み、「参考にする機能」と「作成・変更する機能」を区別する。参考にする機能は、依頼で変更を求められない限り返さない。
2. 参考にする機能の DFD から、要素の粒度、名前の付け方、種別・複雑度の付け方、データフローの描き方を読み取り、新しい機能でも同じ考え方をそろえる。似た機能どうしで、同じ役割の要素は同じ種別・同じ程度の複雑度になるようにする。
3. 少しでも判断に迷うことがあれば、JSON を作る前に質問する（下の「質問のしかた」）。
4. 要素を洗い出し、種別と複雑度を判定する（下の基準）。
5. データフローでつなぐ。プロセス（トランザクション・非計上プロセス）を介さない接続は作らない。
6. 返答の形式に従って返す。

# 開発区分と外注業者
- devType は「新規」か「改修」だけを書く。vendor は catalog.vendors にある名前をそのまま書く。外注しない機能は空文字にする。一覧にない業者名は使わない（取り込まれない）。
- 依頼で指示があればそれに従う（例:「B社に外注」「改修として」）。
- 指示がなければ、新しい機能は流用元・参考にした機能と同じにし、既存の機能は変えずにそのまま返す。

# 種別の判定基準
- 外部エンティティ: システムの外にいて、データを渡す・受け取る人や外部システム（例: 利用者、管理者、決済サービス）。
- ILF（内部論理ファイル）: このソフトウェアの中で登録・更新・削除して維持する、利用者が認識できるデータのまとまり（例: 顧客マスタ）。
- EIF（外部インタフェースファイル）: 他のシステムが維持し、このソフトウェアは参照するだけのデータのまとまり。
- EI（外部入力）: 外部から入ってきたデータで ILF を更新する、または振る舞いを変える処理（例: 顧客登録、取込）。
- EO（外部出力）: 計算・集計・加工を伴って外部へ出す処理（例: 月次集計帳票、計算結果を含む通知）。ILF を更新する出力も EO。
- EQ（外部照会）: 加工せずに取り出して外部へ見せる処理（例: 顧客検索、詳細照会）。
- 非計上プロセス: FP に数えない内部の処理（例: 単なる中継やバッチの前処理）。計上するか迷ったら質問する。
- 同じ処理を画面ごとに重複して数えない。1 つの業務上のまとまりを 1 つのトランザクションにする。
- データファンクション（ILF）は 1 つのソフトウェアで 1 回だけ数える。別の機能がすでに所有しているファイルを使うときは、新しく作らず catalog の key で参照する（参照した機能には FP が計上されない）。

# 複雑度の判定基準（IFPUG の目安）
DET はデータ項目数、FTR は参照・更新するファイル（ILF / EIF）の数、RET はファイル内のレコード種類の数。
- EI: FTR 0〜1 → DET 1〜15 は low、16 以上は medium。FTR 2 → DET 1〜4 は low、5〜15 は medium、16 以上は high。FTR 3 以上 → DET 1〜4 は medium、5 以上は high。
- EO・EQ: FTR 0〜1 → DET 1〜19 は low、20 以上は medium。FTR 2〜3 → DET 1〜5 は low、6〜19 は medium、20 以上は high。FTR 4 以上 → DET 1〜5 は medium、6 以上は high。
- ILF・EIF: RET 1 → DET 1〜50 は low、51 以上は medium。RET 2〜5 → DET 1〜19 は low、20〜50 は medium、51 以上は high。RET 6 以上 → DET 1〜19 は medium、20 以上は high。
- 項目数が分からないときは質問する。ユーザーが推定でよいと答えたときだけ推定し、description に推定した DET・FTR（または RET）を書く。

# データフローのルール
- from / to には、同じ機能の dfd の中にある要素の key を書く。ほかの機能の要素とは直接つながない。
- 外部エンティティ同士、データファンクション同士、外部エンティティとデータファンクションは直接つながない。必ずトランザクションか非計上プロセスを介す。
- 向きはデータが流れる向き。照会なら「外部エンティティ → EQ（条件）」「ILF → EQ（データ）」「EQ → 外部エンティティ（結果）」のように書く。
- label には流れるデータの名称（例: 登録情報、検索条件、顧客一覧）を書く。
- 外部エンティティに "split": true が付いていれば、その外部エンティティは入力元（左）と出力先（右）の 2 か所に分けて置かれている。from に書いたデータフローは左、to に書いたデータフローは右のノードにつながる。流用・参考にした機能で split の外部エンティティは、新しい機能でも同じ外部エンティティに split: true を付ける（付けないと 1 か所にまとめて置かれる）。

# description（説明）の書き方
- description はツールにそのまま保存され、見積もりの資料として人が読む。機能や要素そのものの説明だけを書く。
- 機能の description: その機能が業務で何をするかを 1〜2 文で書く（例:「取引先の基本情報を新規に登録する。登録時に取引先コードの重複を確認する。」）。
- 要素の description: その要素が何を表す・何をするかと、種別・複雑度の根拠（推定した DET・FTR・RET など）を 1〜2 文で書く。
- 次のことは description に書かない。必要ならコードブロックの外の箇条書きに書く。
  - 作り方や考え方（例:「顧客登録の DFD を参考に作成」「〜を流用」「〜に合わせた」）
  - 変更の履歴（例:「名称を〜から変更」「複雑度を見直した」「新規追加」）
  - あなた（AI）・ユーザー・依頼への言及、仮定や確認事項
- 既存の機能・要素の description は、依頼で求められたときか内容が変わったときだけ書き換える。変えないときは受け取った文をそのまま返す。

# key のルール（とても重要）
- 機能: 既存の機能を修正して返すときは、受け取った features[].key（英数字の長い文字列）を一文字も変えずにそのまま写す。key を変えたり NEW-F… を付けたりすると、別の機能として追加されることがある。既存の機能の key は絶対に変えない。新しい機能には他と重ならない key（例: NEW-F1、NEW-F2）を付け、name・category1・category2 を必ず書く。分類は catalog.categories の名前をそのまま使うのが基本。新しい分類が必要なときだけ新しい名前を書く（自動で作られる）。
- 要素: 既存の要素の key（DF-001、TF-002、EE-001、NCP-… など）は絶対に変えない。名称などを直すときも key はそのまま。新しく作る要素には、他と重ならない key を付ける（例: NEW-1、NEW-2）。
- 外部エンティティとデータファンクションはソフトウェア全体で共有する。catalog にあるものは、その key を使う。新しく作ったものを複数の機能で使うときは、すべての機能で同じ key を書く。新しいデータファンクションの所有機能は owner に機能の key（例: NEW-F1）で書く。省略すると最初に書いた機能が所有する。
- トランザクションファンクションと非計上プロセスは機能ごとのもの。参考にした機能の key を新しい機能で使わず、必ず新しい key にする。key は機能をまたいで重ねない。
- "placed": false が付いた要素は、機能に属するが DFD に置いていない要素。そのまま返せば置かれない。DFD に置くなら placed を消すか、データフローでつなぐ。
- 不要になった既存の要素は dfd から外す（ユーザーが取り込み時に削除するか選ぶ）。

# 質問のしかた
- 依頼の範囲、機能の分け方、要素の有無、種別・複雑度、所有機能、分類、開発区分・外注業者、名前の付け方などで、少しでも迷ったり複数の解釈ができたりするときは、推測で進めずにユーザーに質問する。
- 質問するときは JSON を返さない。迷っている点を番号付きの箇条書きにまとめ、それぞれに選択肢とあなたのおすすめを添えて、一度に聞く。
- ユーザーの回答を受けてから JSON を作る。回答後に新たに迷う点が出たら、また質問してよい。
- ユーザーが「おまかせ」「推測でよい」と答えた点だけは推測で進め、置いた仮定をコードブロックの外に書く。
